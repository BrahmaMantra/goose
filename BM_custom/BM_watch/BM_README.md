# Rust 评论队列与 Goose 运行时

当前实现包含独立 API library、单个常驻后台、持久化队列、进程内 Goose 执行，以及 Goose 桌面管理页面。桌面启动的后台已加入官方创作者页面评论读取；真实发送仍关闭。

## 已实现

- 一个 `BM_watch` 进程持有共享的 Goose `StateMachineServices`，按批次处理评论；不调用 `goose run` 子进程。
- 账号/作品/评论标识去重，SQLite 私有落盘；暂停状态持久化，空队列不调用模型。
- external 专用会话显式设置空扩展集合，只有 Goose 原生 `recipe__final_output`；不加载管理员 Plugin、Skill 发现或代码执行工具。


原生测试证实当前 Goose 在状态机里自动提供 `load_skill`，不受扩展列表控制。因此增加了最小的 `StateMachineServicesConfig.BM_disable_skills`：默认 false；本后台设置 true，不注册 SkillOperation 的发现、加载和快捷命令路径。它是运行时级开关，不是完整角色系统。评论后台不在同一 Runtime 内执行管理员工具会话。

- 候选回复仅从已被 Goose 接受的结构化输出提取，由程序添加可配置 AI 标记，并受最终回复长度限制；触发前先检查拒绝词。
- 本地管理 API 使用 Bearer Token，拒绝带 Origin 的管理请求；状态接口只返回计数，记录接口仅向授权管理员返回私有评论与候选回复。
- 官方 Webhook 按原始请求体验签，校验应用/账号，按 Msg-Id 私有记录，支持 challenge。
- 发送尝试状态先落盘；发送中崩溃转为 unknown，不自动重发。

实际二进制目前使用禁用写入的平台适配器：未批准候选进入 review，已批准候选进入 approved 等待发送，均不能发送真实评论。合成测试通过模拟平台验证提交、失败与恢复语义。Webhook content 的实际应用字段尚未核实，原始事件只记录，不猜测解码后自动回复。认证的 `/BM/messages` 接收归一化评论，供适配器和本地测试使用。

## 候选回复审核

桌面「评论值守」提供 **自动审核 ON/OFF**，创建私有配置时默认 OFF，旧配置缺少 `BM_rules.BM_auto_review` 时也按 false 处理。

| 设置或结果 | 行为 |
| --- | --- |
| OFF | 所有准备发送的候选均待人工审核，不调用审核模型 |
| ON，明确低风险 | 规则检查通过后，独立审核会话检查原评论与候选；只有 low + benign 才自动批准 |
| 有风险、不确定、审核失败或超时 | 待人工审核，显示固定审核原因 |
| 空正文、超长或控制字符 | 待审核但不可批准，需要修正生成问题 |
| 命中原有拒绝词或自己的 AI 回流 | 跳过，不进入候选审核 |

低风险以普通问候、测试留言、一般交流和无敏感内容的知识回答为范围。提示词注入、内部指令/凭据索取、隐私、有害内容、高风险专业建议、冒充身份或现实承诺转人工。规则守卫是部分确定性拦截，模型审核不保证识别所有风险；遇到无法确定的情况按待审核处理。审核 DTO 只包含风险枚举与原因码，队列审计和桌面不展示模型推理过程。

「批准此回复」绑定当前记录 ID 和界面展示的完整正文；状态变化或正文不一致返回冲突，不重新生成已批准回复。「跳过」也可撤回尚未发送的已批准回复。ON 不批量批准已有待审核记录；切换 OFF 撤回未发送的自动批准记录，人工批准保留。提交中、平台已接受、结果未知不允许重复批准或重新发送。

状态为 `queued → processing → review / approved → sending → accepted / unknown`。`approved` 在桌面显示「已批准，等待发送」，当前 `BM_NoWrites` 下不会进入 sending。审核授权和平台发送能力是两个独立条件；接通发送器后，已批准记录会在值守运行时消费，管理员可先跳过不希望发送的旧批准记录。

实现分层：`BM_review` 定义审核接口、规则守卫与审计 DTO；`BM_prompt` 提供独立审核 Recipe；`BM_runtime` 用同一个共享 Goose Runtime 的新隐藏会话运行审核，没有 Skill、管理员工具或私有回复背景。生成与审核均复用 Goose 的当前模型配置。ON 的普通候选通常额外调用一次模型，格式不合格仍沿用最多三轮及 90 秒时限；规则已判需人工时不调用审核模型。

`BM_store` 将状态与审计事件在同一 SQLite 事务内保存，事件包含审核来源、时间、规则版本、原因和当时正文；桌面展示最近事件，完整历史留在私有 `BM_reviews` 表。升级使用新增表，不删除旧评论或候选。审核设置在私有配置中保存，同时更新后台 SQLite 策略；重启以配置为准。桌面先暂停消费、原子写配置、更新后台策略，再恢复之前的运行状态；失败时不主动恢复，提示检查或重启。切换时在途生成/审核通过 generation 校验失效，避免沿用旧设置。

这个开关不修改 Goose 的 `GooseMode` 或工具权限。管理 API 仍需管理员 Token 并拒绝 Origin，网页和外部评论不能调用审批或改开关。停止状态下在桌面修改配置，下次启动生效；连接新后台时可以即时切换，旧后台需先停止并更新。

## 本地命令

在 `BM_custom` 运行 `just` 查看中文说明：

```sh
just watch-build
just watch-test
just watch-start /path/to/private/BM_watch.local.json
just watch-status /path/to/private/BM_watch.local.json
just watch-resume /path/to/private/BM_watch.local.json
just watch-stop /path/to/private/BM_watch.local.json
```

`watch-start` 前台启动服务，新队列默认暂停；`watch-resume` 才启用消费。范围内的人工评论（包括账号自己的人工评论）若未命中拒绝词，就通过 Goose 调用配置的 LLM；命中拒绝词或识别为自己 AI 回复的内容进入 skipped。`watch-stop` 暂停消费和新的提交，保留进程及数据。桌面端启动的后台使用 detached 进程和私有日志，关闭窗口或退出桌面应用后继续运行；没有自动安装 launchd，机器重启后需要重新启动后台。

测试只使用临时目录、回环 HTTP、合成评论和模拟模型。`watch-test` 中包含真实 Goose Runtime 与模拟 OpenAI 响应的测试，不调用外部模型服务。

## Goose 桌面入口

在 `BM_custom` 运行 `just watch-build`，会同时准备桌面需要的后台二进制。已有桌面构建产物时用 `just start_goose_desk_debug` 启动；首次准备桌面环境用 `just build_goose_desk_debug`。

侧栏选择“评论值守”，然后：

1. 点击“创建新配置”，在独立的抖音官方窗口扫码登录；回到页面点击“已扫码，读取账号”，从自动读取的作品列表勾选一条或多条作品，填写拒绝词和 AI 回复标记后保存。也可点击“选择私有配置”，在页面内的已保存配置列表中点选账号；列表显示昵称（可读取时）、抖音号、作品数量及当前配置，不打开系统文件选择器。管理 Token 和配置路径留在 Electron 主进程。
2. 点击“启动后台”，或连接已经启动的同一后台。新队列默认暂停；点击“开始值守”才启用读取和消费。读取器登录失效时会显示独立的官方扫码窗口，登录账号必须与当前配置一致。
3. 查看队列计数、私有评论和候选回复，支持分页与跳过待审核/失败记录。
4. “暂停值守”保留进程；“停止后台”先暂停、再请求退出。关闭窗口不停止后台，重新打开页面会读取私有绑定并重新连接。

运行时的作品范围、拒绝词、AI 回复标记和间隔由认证后的任务接口返回。修改配置文件不会自动改变正在运行的任务，停止并重启后台后才生效。后台未连接时页面不加载记录，数据仍保存在原私有目录。桌面在仓库外的私有绑定文件中保存管理连接（端口和 Token）；已绑定配置被删除或损坏后，重新打开桌面仍可查询、暂停和停止已启动的后台。启动或恢复值守仍要求配置有效。

调用链是 `BM_WatchView → preload → BM_ipc/BM_manager → BM_watch HTTP API → 队列/Goose Runtime`。IPC 复用 Goose 的已注册主窗口/主 frame 来源校验，不提供任意路径、URL 或命令代理。原有 Goose 聊天后端和模型配置入口保持独立，评论监控仍只有一个 Rust 进程。

桌面调试构建中的后台二进制和中间产物被 Git 忽略，原子替换不会覆盖正在运行的可执行文件内容。

## 触发条件与 AI 回复标记

`BM_rules.BM_deny_contains` 是不区分大小写的文字包含拒绝列表。命中任意一项（例如 `/clear`、`/delete`）立即跳过，不调用模型；空列表允许范围内的人工评论进入模型。它是字面筛选，不改变 Goose 工具权限，也不将评论当作命令执行。旧字段 `BM_allow_contains` 自动按拒绝词语义读取；不要同时配置旧字段和新字段。

自己的人工评论也可触发，仍使用 external 受限 Runtime。只有自己的 AI 回复会跳过：归一化消息可设置 `BM_is_ai_reply=true`；未标注时使用当前 AI 标记前缀和同账号、同作品的已提交回复记录保守防循环。当前标记更换后，旧的 sending/accepted/unknown 回复仍能按记录识别。前缀是显示约定，不是不可伪造的 AI 身份；自己的人工评论若使用同一标记开头，也会被跳过。

`BM_rules.BM_reply_marker` 默认 `【from DeepSeek-V4.1-Flash-1017】`，可在创建配置界面或私有 JSON 中修改成实际模型名称或其他提示。默认版本依据[DeepSeek 官方 API 文档](https://api-docs.deepseek.com/)于 2026-11-06 的说明：`deepseek-flash` 当前由 DeepSeek-V4.1-Flash-1017 提供。API 别名可能随服务升级调整；显示标记不锁定实际模型版本，切换模型或服务版本后应同步修改标记。标记必须包含非空的 `【…】`，不含控制字符，最多 120 字符，并为回复正文留出长度预算。程序在模型输出后添加标记，已带同一前缀时不重复添加；模型只决定正文及是否建议发送。标记和分隔空格计入 `BM_max_reply_chars`，默认总长 200 字符；超长回复保留为待审核候选，不截断或发送。

```json
{
  "BM_deny_contains": ["/clear", "/delete"],
  "BM_reply_marker": "【from DeepSeek-V4.1-Flash-1017】",
  "BM_max_reply_chars": 200
}
```

上面的字段属于 `BM_rules`。此处不调整模型配置；实际模型仍由 Goose 原生配置管理。修改规则需要停止并重启评论后台。桌面检测旧版后台会提示重启并拒绝恢复消费，暂停和停止仍可操作。当前真实发送依然禁用，候选回复也带 AI 标记，但不会自动发送到抖音。

## 中文小助手回复策略

默认回复指令集中在 [BM_comment_assistant.md](BM_prompts/BM_comment_assistant.md)，由应用层 `BM_prompt` 组装为 Goose Recipe。“小助手”仅是内部称呼，对外名称固定为“BrahmaMantra”，使用简体中文、友好自然的一到两句回复，不冒充账号主人。打招呼、感谢、普通表情和测试留言也可以互动；没有明确问题并不自动拒绝。身份问题按“BrahmaMantra”回答，被问到 AI 身份时如实说明。缺少视频上下文时简短询问，不编造账号经历、商品信息或已阅读视频的事实。

防御措施包含角色冒充、提示词注入、改名或改语言、管理命令、索取隐藏指令与凭据，以及通过翻译、编码、分段等方式绕过的要求。外部评论均作为数据；私有回复背景以 JSON 字符串引用并置于固定规则之下，末尾再次确认“BrahmaMantra”的身份与输出约束。Prompt 防御与现有无管理员 Skill/工具的运行时隔离、结构化校验共同使用，不将 Prompt 当作唯一权限边界。

结构化结果仍为 `BM_send` 和 `BM_text`。`BM_send=true` 表示建议回复，正文必须含中文并符合当前字符预算；AI 标记长度预先从预算中扣除。校验失败时在同一 Goose 会话内修正，总计最多 3 轮、90 秒；不会为修正另启模型或 Goose 进程。`BM_send=false` 时正文为空，队列直接标记 skipped，不将内部判断理由变成候选回复。发送端关闭或其他需要人工处理的候选仍进入 review，界面显示“候选回复”。这些状态不代表已提交平台审核。

每份配置可在自己的 `BM_data/` 目录放置 `BM_reply_context.local.md`，填写说话风格和明确允许公开的账号或作品背景。它是可选的私有 Markdown，最多 16 KiB，权限必须为 0600，拒绝符号链接；每次生成时读取，修改后下一条评论生效。不在这里放 Cookie、Token 或不适合发送给模型的私人资料。此文件只补充回复背景，不增加工具、Skill、模型开关或运行权限。修改公共默认指令需要重新构建后台；修改私有背景无需重新构建。

## 官方创作者页面评论读取

桌面启动 `BM_watch` 时，将当前 Electron 可执行文件及应用入口原子保存为该任务私有数据目录中的 `BM_reader.local.json`（0600），并兼容旧环境参数。后台重启可自行读取这份配置，不依赖发起启动的桌面进程仍持有最新环境参数。Rust `BM_source` 在一个异步采集任务里复用同一个浏览器读取进程，读取所选作品后将归一化评论直接交给 `BM_Store` 入队；模型、队列和生命周期仍由同一个 Rust 后台持有，不为每条评论启动 Goose 或浏览器进程。后台停止时结束读取器，关闭桌面不会结束它。浏览器本身使用 Chromium 的多进程机制。

读取器入口为 `BM_entry → BM_commentReader`，不会启动普通 Goose 桌面窗口、聊天服务或管理员 IPC。它从受保护的配置读取目标，在官方首页核对可见抖音号，再进入每条已选作品的“评论管理”页。只观察官方页面自身发出的 GET 评论列表请求与响应，不直接请求未授权的 OpenAPI、不自行构造内部请求签名。`BM_commentPage` 单独负责 URL 范围校验与两种已核对的页面响应结构。旧作品的评论 ID 映射仅来自页面自身的作品摘要响应；返回队列前再次核对登录账号。

使用官方评论 ID 去重；其他用户使用独立的 `creator_uid:` 引用，官方“作者”标签映射为当前配置账号。昵称不用于判断是不是自己。页面来源没有可靠的 AI 来源字段，因此 `BM_is_ai_reply` 保持 false，自己的 AI 回流依靠标记和历史提交记录过滤。

每轮按所选作品顺序读取，间隔沿用 `BM_interval_seconds`；读取耗时超过间隔时不积压定时任务。沿用官方页面默认排序，兼容无评论时的 `comments: null` 终止页，通过页面加载更多操作补读，每作品每轮最多 20 页、200 条顶层评论。未完成分页时状态为 partial，不宣称读取了全部历史或所有二级回复。首次读取可将当前读到的已有评论入队；后续轮次和进程重启不会重复入队。高流量作品超过此覆盖范围时需要扩展补读策略。

`GET /BM/source` 经管理员 Token 鉴权后返回读取状态、最近读取数量、新增入队数量和检查时间；不会返回 Cookie、账号或路径。桌面显示启动中、暂停、需要扫码、账号不一致、读取成功、分页未完成或读取失败。每次后台启动都会重置来源状态，无读取器时明确显示 manual，不沿用数据库里旧的 ready；成功状态超过读取间隔加 150 秒未更新时，接口返回 stale，提示检查采集。账号不一致时不读取作品、不入队，也不会覆盖原配置的登录快照。

会话 Cookie 通过本机 `BM_cookies.local.json` 显式保存为 0600，补足仅刷新浏览器存储不能可靠保留会话 Cookie 的问题。读取器使用数据目录下的 `BM_reader_browser` 与 `BM_reader_app`，复用自己的持久状态，首次准备才复制登录 profile（跳过缓存），避免同时打开桌面的登录目录。读取器自己的 Cookie 快照及身份差异诊断也只保存在该私有数据目录。网页窗口没有 preload 或 Node 权限，阻止非 GET 评论操作、弹窗、下载和设备权限。

命令行单独启动的后台可复用私有 `BM_reader.local.json`；既无保存的配置、也无兼容环境参数时，提供手动入队与队列处理，来源状态为 manual。私有启动配置权限、大小或格式无效时显示 reader_failed，管理接口仍可用。当前改动不等于获得抖音开放平台应用权限，官方 API library 与网页读取器保持独立；发送器仍为 `BM_NoWrites`，只生成候选回复。

## 私有配置

### 桌面创建与账号切换

已有绑定时，创建和列表均复用绑定所在的统一私有目录，不受再次启动时环境变量变化影响。首次创建目录优先使用当前绝对路径 `GOOSE_PATH_ROOT` 下的 `BM_watch/`，未配置时使用 `~/.goose/BM_watch/`。所有桌面配置 JSON 直接保存在这个统一目录；“选择私有配置”直接列出这里有效且权限符合要求的 `BM_watch*.local.json`，排除未保存配置、备份、浏览器目录和无效文件。页面只传递受校验的配置 ID，不能指定任意路径。目录必须位于 Git checkout 外，检测到仓库、符号链接或不符合要求的权限时拒绝创建，不自动修改已有目录权限。

新建配置才分配登录数据目录；选择、启动或重启不会分配新目录，直接复用已绑定的配置及其数据路径。目录结构如下：

```text
BM_watch/
├── BM_watch_<config-id>.local.json
├── BM_watch_<other-config-id>.local.json
└── BM_profiles/
    └── BM_profile_<random-id>/
        ├── BM_account.local.json
        ├── BM_browser/
        └── BM_data/
```

| 文件或目录 | 内容 |
| --- | --- |
| 根目录 `BM_watch_<config-id>.local.json` | 值守范围、规则、随机管理 Token 与数据目录 |
| `BM_account.local.json` | 官方首页显示的昵称、抖音号、观察时间与浏览器目录引用 |
| `BM_browser/` | Electron 持久化登录状态，含 Cookie 与页面存储 |
| `BM_data/` | 该配置独立的队列、日志、评论会话和读取器状态 |
| `BM_cookies.local.json` | 官方扫码登录的私有 Cookie 快照 |

JSON 为 `0600`，私有目录为 `0700`；浏览器内部文件由 Electron 管理，并由外层私有目录限制访问。真实资料不写入公开源码或测试。Git 忽略规则只作额外防护，主要保证是拒绝在任何 Git checkout 内保存。

准备选择目录时，会将旧的根目录 `BM_profile_*/BM_watch.local.json` 复制为统一目录中的配置文件，保留 Token、原有数据路径和旧文件，使已绑定配置继续可用。复制结果使用稳定文件名，后续启动或选择不会重复生成副本，也不会覆盖用户后来编辑的统一目录配置。旧登录目录与队列不移动、不删除。

扫码窗口没有 Goose preload、Node 权限或管理 IPC；限制 HTTPS 抖音域名的顶层导航，禁用新窗口、下载和设备权限。账号读取复用 `BM_browser_account.py` 已核验的可见账号头部约定；页面结构不符时拒绝猜测。关闭未保存的扫码窗口、取消创建或离开创建页，会清除该未完成会话的认证存储；目录可能保留，但没有可选的值守配置。保存前再次读取账号，防止扫码期间切换账号。

保存成功会绑定配置，不启动后台或模型。桌面从当前账号的官方作品管理页读取作品，不再要求手填作品链接。主进程仅接受当前确认账号已经读取的作品 ID，读取前后及保存前复核账号。该检查不等于 OpenAPI 作品归属授权，网页登录路线只读取官方评论管理页面正常加载的评论，真实发送仍未启用。页面抖音号不是 OpenAPI `open_id`，网页登录状态不能当作开放平台授权，OpenAPI 适配器接入前必须确认身份映射。

### 作品勾选与顺序

官方新版作品管理的默认排序是“最新发布”，另提供“最高播放”“最高点赞”，置顶作品带独立标记。依据在线读取的[官方内容模块入口](https://creator.douyin.com/goofy/douyin_creator_pc/mono/creator_content)及其公开加载的管理组件确认。这里读取新进入作品管理页面的实际排序文字与 DOM 顺序，保留置顶标记，不自行重排；个人主页的置顶展示不作为作品管理列表的排序依据。

确认扫码账号后自动读取首批作品。“加载更多作品”逐步扩大读取范围，保留勾选；“刷新作品列表”重新读取并清空勾选。官方页面通过滚动加载，应用使用该页面的滚动容器，不自行调用其内部列表 API。每次先复核账号，再从官方页面重新读取扩大后的范围，最多展示 100 条；结果始终 `BM_complete=false`，停止加载或未发现新增条目不能当作完整作品库。

列表展示标题、页面显示的发布时间、状态与置顶标记，不读取媒体/封面签名链接。对于可查看详情的卡片，仅触发其已核验的根节点只读详情入口，由 Electron 拦截 `window.open` 并从官方详情路径解析作品 ID，始终拒绝打开新窗口。不会点击封面预览、编辑、删除、置顶或其他作品操作。标题在触发前复核，页面变动、详情不可用或未取得可信 ID 的条目不可勾选。详情解析和列表等待均有时限，日志仅记录数量与固定状态。

作品逻辑与 DTO 在 `ui/desktop/src/BM_watch/BM_works.ts`，勾选组件在 `BM_WorkPicker.tsx`，窗口归属、账号复核和受限 IPC 沿用 `BM_login/BM_ipc`；没有新增模型配置、MCP 或 Goose 内核改动。测试覆盖页面顺序与隐藏卡片、只读根节点点击、官方 ID 来源、跨批次选择及主进程拒绝未读取 ID；原生 Electron 合成页面检查验证 12 条作品 ID 解析与私有保存，读取期间只有管理窗口和登录窗口，没有创建详情窗口。

“已扫码，读取账号”是页面观察，不执行自定义抖音鉴权，也不写配置：抖音官方页面负责扫码登录，Electron 主进程检查请求来自 Goose 已注册主窗口及主 frame，并确认扫码窗口属于该窗口、页面位于官方首页，然后读取可见账号头部。包含图标或嵌套文本的账号标签按最深匹配元素定位。昵称按官方首页组件的 `header > left > name` 结构提取，兼容普通 `div` 和账号切换按钮内的 `span`；CSS module 类名只匹配字段前缀，不依赖构建哈希。保留此前核验的直接父节点昵称按钮布局，无法唯一确定时拒绝猜测。

该结构依据 2026-11-06 在线读取的[官方首页入口](https://creator.douyin.com/goofy/douyin_creator_pc/home/index.html)及其公开加载的首页组件资源确认。资源只用于核对可见 DOM 布局，不执行资源代码，不访问其中的内部 API，不将真实页面或账号资料写入仓库。

读取有 8 秒超时，失败不会一直阻塞后续取消操作。页面在扫码按钮附近显示具体原因，终端仅记录固定状态码，例如 `BM_account_header_missing`、`BM_account_name_missing`、`BM_window_unavailable` 或 `BM_read_timeout`；不记录账号值、完整 URL、HTML、Cookie 或原始异常。开发版主进程热重载后需要重新打开扫码窗口。

扫码窗口由 Electron 内置 Chromium 提供，不依赖额外安装系统浏览器。窗口机制本身跨平台；当前私有文件权限检查和 Rust 后台仍有 Unix 平台假设，Windows 整体值守流程尚未适配验证。

切换账号：先“停止后台”，再“选择私有配置”，在页面列表中点击另一份已保存配置，然后启动后台并开始值守。每份配置的数据和登录状态独立保留；选择配置本身不自动重新登录，也不新建浏览器目录。登录过期后需要重新扫码创建配置，目前不提供已保存 profile 的重新授权入口。

模型仍由 Goose 原生配置管理。创建时有 `GOOSE_PATH_ROOT` 就引用它；没有时 `BM_goose_root` 保存为 `null`，后台使用 Goose 的操作系统默认配置位置，不创建第二套模型配置。

复制 [BM_watch.example.json](BM_config/BM_watch.example.json) 到仓库外目录，再按本地环境修改。配置文件权限必须为 0600，数据目录必须为 0700 且位于 Git checkout 外。管理 Token 至少 24 字符，请使用随机值；不把配置、队列、评论、凭据或 Goose 会话加入 Git。

`BM_goose_root` 指向已有 Goose 配置根，模型由 Goose 原生配置解析；不更改桌面端配置，也不在代码中内置模型密钥。`BM_data_dir` 保存业务 SQLite 与评论运行的独立会话记录。运行时每条评论创建逻辑会话，不创建进程或复制模型配置。

本地接口：

| 接口 | 用途 |
| --- | --- |
| `GET /health` | PID；不含业务数据 |
| `GET /BM/status` | 认证后读取启用状态与队列计数 |
| `GET /BM/task` | 认证后读取进程实际使用的任务规则和间隔，无凭据 |
| `GET /BM/records?BM_before=id` | 认证后分页读取私有评论与候选，每页最多 50 条 |
| `POST /BM/skip` | 认证后跳过待审核/失败/已批准记录，其他状态返回冲突 |
| `POST /BM/approve` | 管理员批准当前正文，body 为 `BM_id` 与 `BM_reply`；只接受待审核记录，重复/正文变化返回冲突 |
| `POST /BM/review-policy` | 管理员更新运行策略，body 为布尔 `BM_auto_review`；桌面同步保存私有配置，直接 API 调用不改配置文件 |
| `POST /BM/shutdown` | 认证后暂停并请求后台退出 |
| `GET /BM/source` | 读取器状态、数量和检查时间；管理员鉴权 |
| `POST /BM/messages` | 认证后写入归一化评论；只接受配置的账号和作品 |
| `POST /BM/resume` / `/BM/pause` | 认证后启用或暂停 |
| `POST /BM/webhook` | 独立平台验签；原始事件私有记录与去重，不运行模型 |

服务仅监听回环地址。真实 Webhook 仍需要平台注册并可达的入口；不能把本地监听地址当作已完成平台订阅。

## 下一阶段的验收前提

核实当前应用的权限、评论字段、分页覆盖与发送回执，然后实现实际适配器和事件归一化。API library 的模拟协议测试不证明当前账号有权限。官方回复接受与审核/展示状态必须区分；缺少幂等或回查能力时不能承诺 exactly-once。

架构见 [单进程设计](../BM_docs/BM_comment_watch_design.md) 与 [API 分层](../BM_docs/BM_douyin_api_design.md)。新增 Rust API 不依赖 Goose、persona、队列或数据库；队列通过平台和生成器接口验证，Goose 适配集中在一个模块。
